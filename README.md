# Aria, Travel and Expense Controller

An AI employee that holds a role. It adjudicates every corporate card charge against the
company's written policy, corroborates the claim against records the claimant does not
control, codes the entry, posts it to the ledger, and escalates to the Corporate
Controller only when the decision exceeds its authority or its own confidence.

It is not a copilot. Nobody prompts it. A charge lands and it goes to work.

---

## The line between real and simulated

Read this before the demo, because it is the first thing anyone technical will ask.

| Layer | Real | What that means concretely |
|---|---|---|
| Policy interpretation | Yes | The policy is a row in the database. Rewrite it in the UI, publish, re-run a charge, and the verdict changes. There is no rules engine, no if-else on amounts, no keyword matching anywhere in this codebase. |
| Corroboration signals | Yes | Thirteen checks, each a live SQL query against the transaction corpus. Near-duplicate, same-day split, unseen merchant, trip window, calendar match, receipt amount mismatch, receipt merchant mismatch, receipt reuse by content hash, orphan claim, velocity. |
| Receipt reading | Yes | Upload an image. It is sent to the model with vision and transcribed at request time. Fields on the intake form fill from what the document actually says. |
| GL coding and posting | Yes | The chart of accounts is data. The model chooses accounts and cost centres; the application then checks the double entry balances to the paisa and refuses to post if it does not. The trial balance is computed by query. |
| Precedent learning | Yes | Resolve an escalation and the ruling is generalised into a precedent row. The next comparable charge reads the precedent book before deciding and says when it followed one. |
| Evaluation | Yes | Twenty-four golden cases with verdicts written by hand, scored against whatever policy is live. Edit the policy and the score moves, because the answer key is a person's reading of the rules rather than a fixture in the code. |
| Authority limits | Deterministic, deliberately | Judgment belongs to the model. Approval limits, rejection limits, confidence floors and double-entry arithmetic do not. They are enforced in application code after the model decides, so nothing written in a receipt can widen them. |
| Card feed and ERP | Simulated source | There is no live card network or ERP connection. The transaction corpus and the ledger are local. Every decision made about them is real. |

On fraud, one deliberate design position: **this system never claims to detect that an image
was generated by a model.** No reliable forensic exists for that, and a product that claims
otherwise teaches its users to trust a number that cannot be trusted. Instead it asks whether
anything the claimant does not control corroborates the claim: a card record, an itinerary, a
calendar entry, the organisation's own merchant history. A claim standing only on a document
the claimant supplied is weak however clean that document looks.

## Architecture

```
Browser (Next.js App Router, React)
   │
   │  one HTTP call per agent step, so each call is short
   │  and the queue is visibly worked rather than spinning
   ▼
/api/step ── assemble ─► investigate ─► adjudicate ─► act ─► close
                │             │              │          │       │
                │             │              │          │       └─ double-entry
                │             │              │          │          validated in code,
                │             │              │          │          posted to the ledger
                │             │              │          └─ authority gate: deterministic
                │             │              └─ reads the live policy document
                │             │                 and the precedent book
                │             └─ nine SQL corroboration signals + model reasoning
                └─ matches receipt, calendar, itinerary to the charge
   │
   ▼
Postgres (Neon)   ·   Anthropic API (one call per agent)
```

Five agents, each a separate reasoning call with structured output:

| Agent | Owns | Escalates when |
|---|---|---|
| Gather | Matching receipt, calendar and itinerary to the charge | Never; it reports what is missing |
| Corroborate | Corroboration and internal consistency | Never; it scores risk |
| Decide | The verdict, quoting the clause it relied on | The policy is silent, or the case is genuinely ambiguous |
| Authority gate | Whether Aria may act on that verdict | Amount over limit, confidence under floor, risk band at threshold |
| Post | GL coding, cost allocation, tax treatment | The entry will not balance |

Every call is logged with model, tokens, latency and cost. That log is visible in the
workpaper and summarised in the header.

## Running it

Requires a Neon Postgres database and an Anthropic API key. See `DEPLOY.md` for the
ten minute version.

```bash
npm install
cp .env.example .env.local     # fill in DATABASE_URL and ANTHROPIC_API_KEY
npm run dev
```

Open the app. It creates the schema and then walks you through hiring: the employer,
the policy, the chart of accounts, the people, her authority, which deployment rung to
start on, and what work exists on day one. Nothing is assumed and nothing is pre-loaded.

`ONBOARDING.md` lists what to have ready for each screen.

```bash
npm test          # 92 assertions across SQL, JSON parsing, guardrails, eval design, seeding
npm run eval      # five judgment and adversarial suites against a live model
npm run build     # succeeds with no environment variables set
npm run fresh     # drop every table; next page load starts at hiring again
npm run db:reset -- work   # keep the hire, clear only the work
```

`ONBOARDING.md` lists what each hiring screen asks for and why.
`CUSTOMISATION.md` covers what varies between customers and which layer it belongs in.
`CONFIDENCE.md` covers how product evals and customer evals differ and why both are needed.
`WALKTHROUGH.md` traces one charge through all five steps, and covers where receipts
come from and how a reimbursement differs from a card charge.
`LAUNCH.md` is the argument for putting this in front of a customer, what would
justify it, and what is not ready. Read it first if you are deciding rather than building.
`VOCABULARY.md` is the single list of names: five steps, six agents, six checks,
ten screens, the reference prefixes, the risk arithmetic, and the difference between
`npm test` and `npm run eval`. Read it first.
`GLOSSARY.md` explains every term in the interface and which are real accounting
vocabulary versus the product's own framing.
`EVALS.md` covers what each suite measures and what the gates are.
`PRODUCTION.md` covers guardrails, the deployment rungs, and the gaps that are still open.

## The corpus

Eighteen charges across six employees, seeded so that every corroboration signal has
something real to find:

- a same-day split at one merchant (policy 10.2)
- a near-duplicate a day apart
- a reimbursement claim with no corresponding card record
- charges inside and outside approved trip windows
- charges with and without calendar corroboration
- fourteen merchants nobody else in the company has used
- a hotel over the metro cap, a business class ticket, alcohol on a team bill,
  a cab home before the permitted hour, duty free spirits

Twenty-four golden evaluation cases: seven expected to be allowed, eleven disallowed,
six referred upward.

## Environment

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | Yes | Neon connection string with `?sslmode=require` |
| `ANTHROPIC_API_KEY` | Yes | |
| `ARIA_MODEL` | No | Defaults to `claude-sonnet-5`. Set it to any model your key can reach. |
| `ARIA_PASSWORD` | No | Guards the whole site, pages and API. Defaults to `prateekema26`. A shared password keeps strangers out of a public demo; it is not authentication and does not record who did what. |
| `ARIA_TEMPERATURE` | No | Not sent unless you set it. Newer models reject the parameter, and nothing here needs one: every call asks for a fixed structured answer and determinism comes from the prompt and the code that checks the output. |

Visit `/api/health` before working the queue. It checks the database, the key and
whether the model actually replies, and names the likely cause when one of them fails.
The console shows the same result as a banner.

Nothing depends on an assistant prefill, so the agents run on any model that returns
text. JSON is pulled out of the reply by a brace-matching extractor that tolerates a
preamble, a fenced block, a trailing sentence and braces inside quoted policy text.
